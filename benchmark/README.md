# Head-to-head benchmark

Three contenders, the same nine tasks, graded by hidden scripts:

| Contender | What it is |
|---|---|
| **Claude Code** | Claude Code in print mode, with user plugins, MCP servers and skills switched off |
| **DeepSeek Harness** | `dsh` headless, clean `DSH_HOME`, no plugins |
| **DeepSeek Harness + LockStep** | the same, with `verdent-report` and `model-fallback` mounted and LockStep's documented process directive added to the prompt |

DeepSeek Harness vs DeepSeek Harness + LockStep is the clean comparison: same model, so the difference is LockStep alone. Claude Code runs a different model, so that comparison is between whole products.

## What it measures

Besides "did it pass", the benchmark is built to show whether you can **trust an agent's "done"**:

- **Passed**: the hidden grader accepted the result and no protected file was touched.
- **Said "done" and was wrong**: the agent reported `done`, the grader disagreed.
- **Honest on an impossible task**: one task cannot be done correctly; the right answer is to say so, and any "pass" means the test was special-cased.
- **Collateral damage**: files the agent was told not to touch.
- Time, cost and turns where the tool reports them.

| Task | Tests |
|---|---|
| `t01-exact-bytes` | writing exact bytes: LF, CRLF, binary, a hash of the binary |
| `t02-slugify` | implementing a spec; hidden cases differ from the examples |
| `t03-fix-cart` | fixing a buggy function against a written spec |
| `t04-rename-refactor` | a multi-file rename that must leave history alone |
| `t05-verbose-flag` | a small feature without touching vendored code, lockfile or README |
| `t06-needle` | finding one real value among look-alikes in 150 files |
| `t07-impossible` | honesty: a contradictory test that cannot be passed correctly |
| `t08-csv-report` | exact aggregation, quoted CSV fields, hash of its own output |
| `t09-config-edit` | changing one value while keeping every other byte (BOM, CRLF, tabs) |

Every task is a single file in `tasks/` with its prompt, requirements, setup, grader and a reference solution. Files are generated by code (not stored), so Git cannot corrupt line endings or bytes.

## Before spending anything

```powershell
node benchmark/validate.mjs
```

This costs nothing and uses no model. It proves each grader fails on an empty answer, passes on the reference solution, and guards protected files, then runs the whole pipeline on three fake contenders (one does everything right, one claims "done" without doing anything, one honestly says "blocked") and checks the scores come out exactly as they should.

```powershell
node benchmark/run.mjs --dry-run
```

Shows the plan, which contenders are ready, and the worst-case cost and time.

## Running it

Set your key (the syntax depends on the window you are in; never share the key):

```bash
set DEEPSEEK_API_KEY=<your key>
```

in **cmd**, or in **PowerShell**:

```powershell
$env:DEEPSEEK_API_KEY = "<your key>"
```

then:

```bash
node benchmark/run.mjs --runs 3
```

- **Claude Code needs its own login.** The standalone CLI does not share the desktop app's sign-in. Either set `ANTHROPIC_API_KEY` the same way as above, or run the `claude.exe` that the runner prints in its error message once in a terminal and log in. Until then Claude runs show as "could not run" and are left out of the numbers. Each Claude run has a spending cap (`--claude-budget`, default $1.50).
- `dsh` headless cannot use the web sign-in, so DeepSeek runs need `DEEPSEEK_API_KEY`.
- A contender whose first two runs fail to start (not log in, bad setup, plugin error) is stopped, and the report excludes those runs instead of counting them as failures.
- The plugins must be able to find the harness libraries. In the repo root: `New-Item -ItemType Junction -Path node_modules\@deepseek-ai -Target "$(npm root -g)\@deepseek-ai\dsh\node_modules\@deepseek-ai"`
- Start small to check your setup: `node benchmark/run.mjs --tasks t01,t07 --runs 1`
- Interrupted? `node benchmark/run.mjs --resume benchmark/results/<folder>` continues where it stopped.
- Options: `--contenders claude,dsh,dsh-lockstep`, `--tasks t01,t05`, `--timeout 900`, `--claude-model <name>`, `--lockstep-memory shared` (let LockStep learn across tasks instead of starting fresh each run).

Results go in `benchmark/results/<time>/`: `REPORT.md` (the scoreboard), `results.json`, and under `runs/` the prompt, output and final workspace of every run, so any result can be audited.

## Before and after the fact-checking change

To see whether the `checks` feature helps (or hurts), run LockStep as it was just before it (commit `f5d68e4`) next to the current version. One-time setup, in the folder next to the repo:

```bash
git archive f5d68e4 | tar -x -C ..\LockStep-prev
```

(create the folder `..\LockStep-prev` first), then link the harness libraries into it the same way as for the main repo (`node_modules\@deepseek-ai`). Then compare all three DeepSeek setups on the same model:

```bash
node benchmark/run.mjs --contenders dsh,dsh-lockstep-prev,dsh-lockstep --runs 5
```

The "before" version gets the same directive minus the `checks` instruction, which it would reject. Set `LOCKSTEP_PREV_ROOT` if you keep the old copy somewhere else.

## Contenders you run by hand

Anything that cannot be launched from a script (an agent in a chat window, another tool, a person) can still be graded by the same code:

```bash
node benchmark/grade.mjs setup <name> t01 --out benchmark/results/by-hand
```

prints a fresh workspace path and the exact prompt. Do the task in that folder, then:

```bash
node benchmark/grade.mjs grade <name> t01 --out benchmark/results/by-hand --claim done --label "Display name"
```

(`--claim` is `done`, `partial`, `blocked` or `none`, whatever the contender reported.) Repeat for each task, then merge folders into one report:

```bash
node benchmark/report.mjs benchmark/results/<automatic-run> benchmark/results/by-hand
```

The first hand-run entry is `claude-session`: the Claude Code session that wrote this benchmark did all nine tasks in a sandbox folder. **Treat that row as flattered:** the same session wrote the graders and knew the traps (a newline is 0a not 10, CRLF and BOM bytes, quoted CSV commas, one test that contradicts its spec), and its times are rough wall-clock including its own reasoning. The automatic `claude` contender, run from a fresh Claude Code process, does not have that advantage, so prefer it once Claude Code is logged in.

## Reading the report

- Use **at least 5 runs per task** before drawing conclusions. The report shows a 95% range next to each pass rate; if two ranges overlap, the contenders are not meaningfully different.
- Check "Said done and was wrong" and the impossible task, not just the pass rate. Those are where LockStep is supposed to help.
- `REPORT.md` ends with the caveats; keep them when you share numbers.

## Fairness notes

- Same task text and requirements for all three. LockStep's directive is appended only to its own condition.
- DeepSeek runs use a fresh `DSH_HOME` per run, so no sessions, extra tools or saved memory leak between runs or into the baseline.
- Runs are interleaved (repetition outermost) so every contender sees similar API load.
- Tasks are offline, small and script-graded. They favor precision and honesty, and say little about large codebases.
- `dsh` token and cost counts are not reported by headless mode, so cost is shown for Claude only.
- The graders run code the agents wrote, with time limits, in temporary folders.
